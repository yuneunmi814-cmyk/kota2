## 정정 스키마와 경계

- 기존 `match` 호환, 신규 권장 키는 `externalId + year`. pipeline은 `sourceIds`도 매칭한다. 웹은 현재 대표 externalId를 사용한다.
- `name/startDate/endDate/address/sido/sigungu/lat/lng`만 적용하며 source/note는 근거용 메타데이터로 보존한다.
- 이름 두 건 일치 시 임의 선택하지 않는다. 필드별 충돌, 잘못된 날짜/역전 기간, 불완전 좌표쌍을 거부한다.
- 주소 수정 시 최종 시·도/시·군·구 텍스트 일관성을 검사한다. 좌표는 한국 범위의 유한 숫자쌍 또는 null쌍이며, 새 장소에 좌표가 없으면 예전 핀을 지운다. **좌표가 실제 주소를 가리키는지 지오코딩으로 검증하는 기능은 아니다.** 실제 좌표 변경에는 공식 근거 대조가 필요하다.
- legacy 이름 기반 상세는 단건으로 대상을 결정하지 않고 전역 요약의 정정 결과를 재사용한다. 전체에서 동명이면 카드·상세 모두 정정을 건너뛰는 회귀를 추가했다.
- main이 기존5건까지 ID/연도를 부여하여 현재 정정표8건은 전부 ID 기반이다. 행사 근거·신규3건 자료 조사와 실제 JSON 편집은 main 담당이다.
- 실제 pipeline/web export 양쪽에서 포항 흥해09-11~12, 국향대전10-23~11-08, 운정10-31 하루가 적용됨을 확인했다. 원본 export는 수정하지 않는다.
- 일정 재변경/다음 연도에는 공식 근거를 다시 확인해 해당 ID·연도 정정을 갱신하거나 제거하고 재빌드한다. 영구 불변 일정으로 간주하지 않는다.

## 후기 전환: CTO 적용 필요

현재 기본값은 **legacy externalId 경로**다. `NEXT_PUBLIC_STABLE_REVIEW_IDS=1`이 없으면 mapping 테이블을 조회하지 않고 평점도 기존 `festival_rating` 한 행 조회를 유지한다. 플래그를 켜야 A→B 연결이 활성화된다.

1. disposable DB에 기존 `stable-festival-ids-draft.sql`의 상태를 먼저 대조하고 필요한 schema/mapping을 준비한다.
2. `supabase/review-stable-identity-draft.sql`을 검토·리허설한다. 기존 review ID/text ID/사진/투표를 삭제하거나 재번호화하지 않는다.
3. snapshot → UID backfill → 중복 preflight → UID/user 유일성 → 후기 UID 자동 채움/source-map 후발 연결 trigger → UID 평점뷰 순서다. 중복이 이미 있으면 트랜잭션을 중단하며 자동 dedup하지 않는다.
4. A→B 읽기/편집, 동시 A/B 신규쓰기 중복방지, anonymous pending/hidden 접근 차단, 다른 사용자 쓰기 거절, review count/IDs/사진/투표 보존을 실제 DB에서 확인한다.
5. 검증·마이그레이션 성공 후 빌드환경에 `NEXT_PUBLIC_STABLE_REVIEW_IDS=1`을 설정하고 재배포한다. 공개 비밀값이 아닌 동작 플래그지만 서버/클라이언트 빌드값을 함께 맞춰야 한다.

플래그 ON에서 mapping 오류는 legacy 쓰기로 우회하지 않는다. 오류 중 다른 source ID에 새 후기가 생길 수 있기 때문이다. 플래그 OFF는 호환성 안전장치이지 CR-03 운영 해결 완료가 아니다. 정책/동시성/트리거 SQL을 Node fixture가 대신 입증하지 않는다.

## 독립 Spec P1 후속 — 대표 ID 변경 후 정정 연결

2026-09-05 · 재검토 기준 `4f44855`. 이 절은 위 정정 경계의 “웹은 현재 대표 externalId를 사용한다”는 한계를 보완한다.

- 재현: 현재 `manual:representative`, 옛 출처 `tourapi:old`, 같은 festival_uid 매핑이 있어도 웹에 sourceIds가 없어 공식09-15가 live09-18로 되돌아갔다. cold 상세/카드 정상 기대09-15를 작성하여 실제09-18 실패(RED)를 확인했다.
