# KOTA 기술컨설팅 후속 작업 — 디스코드 팀 공유 자료

기준: 2026-09-01 19:01 KST

대상: KOTA 기획·개발 팀원

현재 상태: 로컬 `main`에 커밋 완료, 운영 배포 전

## 디스코드에 바로 올릴 요약문

아래 3개 메시지를 순서대로 복사해 올리면 됩니다.

### 메시지 1 — 결론과 현재 상태

> **[KOTA 기술컨설팅 후속 작업 공유]**
>
> 8/29 기술컨설팅의 핵심은 화면을 다시 만드는 것보다, 여러 화면에서 함께 쓰는 규칙을 한곳에 모으고 자동 테스트로 보호하는 것이었습니다.
>
> 현재 긴급도가 높았던 항목 중 아래 작업을 완료했습니다.
> - 과거 JIMFF 주소 2개가 404 대신 현재 축제로 이동하도록 복구
> - 서비스의 날짜 판단을 한국 시간 기준으로 통일
> - 주소·자정·시작일·종료일·주말 관련 자동 테스트 추가
> - 빌드 경로와 사이트맵이 상세·사진·번역·실시간 API까지 읽던 구조를 ID 전용 조회로 1차 분리
> - 빌드 과정에서 일부 축제가 누락될 수 있던 정렬 문제 수정
>
> 자동 테스트 10개와 전체 빌드가 통과했고, 과거 JIMFF 주소 2개는 308 이동, 현재 상세 주소는 200 정상 응답을 확인했습니다. 변경사항은 로컬 커밋까지 완료했지만 아직 운영 사이트에는 배포하지 않았습니다.

### 메시지 2 — 컨설팅 항목별 진행 상황

> **컨설팅 권고와 현재 진행 상황**
>
> 1. JIMFF 404 재현 테스트 → **완료**
> 2. 축제 자체 ID / 수집처 ID / 과거 주소 분리 → **부분 완료**
>    - 과거 주소 응급 복구와 장기 설계 완료
>    - 운영 DB 이전은 리뷰·로그 연결을 확인한 뒤 진행
> 3. KST 날짜 모듈로 통일 → **완료**
> 4. 날짜·상태·주말 테스트 → **완료**
> 5. 전체 축제 조회를 목적별로 분리 → **부분 완료**
>    - 경로·사이트맵용 ID 조회 완료
>    - 목록 요약, 달력 기간, 상세 1건 조회는 남음
> 6. 목록 필터·정렬 분리 → **미착수**
> 7. URL·스크롤·위치 상태 분리 → **미착수 / 출시 전 필수 아님**
> 8. 상세 페이지 내부 역할 분리 → **미착수 / 출시 전 필수 아님**
>
> 컨설팅은 위 순서를 일정표가 아니라 ‘앞 작업이 다음 작업의 안전장치가 되는 의존 순서’로 제안했습니다. 따라서 큰 ID 변경을 한 번에 적용하지 않고 단계별 검증 후 진행합니다.

### 메시지 3 — 다음 작업과 팀 확인 요청

> **다음 작업 순서**
>
> 1. 운영 DB의 실제 테이블·컬럼과 이미 끊어진 리뷰·로그 수를 읽기 전용으로 확인
> 2. 새 축제 ID 대장, 출처 연결표, 과거 주소표와 백업·검증·롤백 SQL 준비
> 3. 기존 ID를 유지한 채 새 ID를 병행 적용하고 누락·중복 확인
> 4. 데이터 수집 파이프라인이 동일 축제에 기존 ID를 재사용하도록 수정
> 5. 목록 요약 → 달력 기간 → 상세 1건 순서로 데이터 조회 분리
> 6. 신규 축제가 배포 후 바로 열리는지 실제 시나리오 테스트
> 7. 필터·정렬과 큰 화면 파일 분리는 공모전 마감 이후 또는 여유 시간에 진행
>
> **팀에서 확인할 사항**
> - 현재 두 커밋을 언제 운영에 배포할지
> - 운영 DB 읽기 전용 점검 시간과 접근 담당자
> - ID 이전 결과를 확인할 팀원 1명 지정
>
> 영속 ID 이전은 리뷰·이용 기록에 영향을 줄 수 있어, 확인 없이 운영 DB를 한 번에 변경하지 않겠습니다.

## 컨설팅 항목 외에 함께 해결한 문제

- Supabase 데이터를 여러 묶음으로 읽을 때 시작일이 같은 축제의 순서가 고정되지 않아, 빌드 작업자에 따라 일부 행이 빠질 수 있었습니다.
- 시작일 다음에 ID로 한 번 더 정렬하도록 수정해 매번 같은 순서로 읽게 했습니다.
- 이 수정은 컨설팅의 직접 과제는 아니지만 전체 빌드 검증 과정에서 확인된 실제 안정성 문제입니다.

## 앞으로의 실행 계획

### 1단계 — 현재 수정 배포

- 두 로컬 커밋의 변경 범위를 팀에서 확인합니다.
- 원격 저장소에 올리고 Vercel 배포 후 과거 주소·현재 주소·홈·목록·달력을 다시 확인합니다.
- 문제가 있으면 이번 두 커밋 단위로 되돌릴 수 있습니다.

### 2단계 — 운영 DB 사전 측정

- 실제 운영 DB 구조가 저장소의 SQL 문서와 같은지 확인합니다.
- 리뷰·저장·조회 기록·제보·프로모션이 어느 축제 ID를 참조하는지 집계합니다.
- 현재 축제에 존재하지 않는 옛 ID를 참조하는 기록을 ‘고아 기록’으로 집계합니다.
- 이 단계는 읽기 전용이며 데이터를 변경하지 않습니다.

### 3단계 — 영속 축제 ID 병행 도입

- 삭제하지 않는 KOTA 내부 축제 ID 대장을 추가합니다.
- 하나의 축제에 여러 수집처 번호를 연결합니다.
- 이미 공유된 과거 주소를 같은 축제에 연결합니다.
- 기존 문자열 ID는 바로 제거하지 않고 새 ID와 함께 유지합니다.
- 이전 전후의 총건수·누락·중복을 비교하고 롤백 가능 상태를 유지합니다.

### 4단계 — 수집 파이프라인 연결

- 같은 출처 번호가 이미 등록돼 있으면 기존 KOTA 축제 ID를 재사용합니다.
- 자동 병합이 잘못된 축제를 하나로 고정하지 않도록 병합 근거와 변경 기록을 남깁니다.
- 일정 기간 새 ID 증가량과 연결 실패 건수를 관찰합니다.

### 5단계 — 조회 구조 추가 분리

- 목록은 카드에 필요한 요약 정보만 읽습니다.
- 달력은 필요한 날짜 범위만 읽습니다.
- 상세는 요청한 축제 한 건을 읽습니다.
- 실시간 일정 보정은 별도로 캐시하되 목록과 상세가 같은 날짜를 보여주는지 확인합니다.

### 6단계 — 핵심 안정화 이후 구조 개선

- 목록 필터·정렬을 화면에서 분리하고 자동 테스트를 추가합니다.
- URL·스크롤·위치 상태와 화면 표시를 나눕니다.
- 상세 페이지의 조회·SEO·화면 부분을 나눕니다.
- 기존 린트 오류 5건을 정리합니다.
- 충분히 관찰한 뒤 옛 ID 컬럼 제거 여부를 별도로 결정합니다.

## 현재 위험과 주의사항

1. 영속 ID를 잘못 연결하면 서로 다른 축제가 하나로 굳어질 수 있으므로 자동 병합 결과 검토가 필요합니다.
2. 기존 리뷰·로그가 옛 ID를 참조하므로 운영 DB를 한 번에 교체하면 사용자 기록이 화면에서 사라질 수 있습니다.
3. 배포 뒤 추가된 신규 축제가 재배포 전에도 열리는지는 실제 테스트 결과로 정책을 정해야 합니다.
4. 목록과 상세의 실시간 보정을 따로 나누면 같은 축제의 날짜가 다르게 보일 수 있어 공통 보정 규칙이 필요합니다.
5. 현재 린트에는 기존 React 관련 오류 5건이 남아 있지만, 이번 변경의 테스트와 빌드는 통과합니다.
